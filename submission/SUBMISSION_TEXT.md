## Elevator pitch (50 words)

OpsMind helps small manufacturers find energy waste that production data alone cannot
explain. Deterministic code computes energy intensity, a trailing baseline, deviation and
cost impact; Gemini explains only that evidence, separates facts from hypotheses, and
suggests checks. A person decides what to do, and the before/after result is recorded
without claiming causation.

---

## Short description (150 words)

Operations data is fragmented. Electricity, production, operating hours and weather live in
different sheets, so a power spike rarely gets investigated: comparing periods by hand takes
hours and is hard to reproduce.

OpsMind turns that into a short, auditable workflow. The app calculates energy intensity
(kWh per unit), compares each day with a seven-day trailing baseline, flags deviations above
a 15% prototype threshold, and estimates potential excess cost with a printed formula. Only
then does Gemini receive a minimum structured context of 13 evidence items. It writes a
summary, observations with evidence IDs, hypotheses that list missing evidence, recommended
human checks and explicit limitations. The server validates the answer with Zod, discards
citations to evidence that was not supplied, and stores failures as failures.

The prototype ships with 30 deterministic simulated days, a full action workflow, and a
labelled mock fallback when no API key is configured.

## Problem

Small and mid-sized manufacturers rarely have an energy analyst. Their operational data is
spread across production logs, utility bills, shift notes and weather apps. A sudden rise in
electricity consumption is easy to see and hard to explain:

- production may be flat, so the spike is invisible in output-based reporting;
- comparing a day against “normal” is done by hand, with no stored method;
- a generic chatbot can produce a plausible cause, but cannot show which records it used;
- actions are taken without a before/after record, so nobody learns whether they worked.

The result is avoidable cost, missed equipment checks and no audit trail for decisions.

## Solution

OpsMind is a working prototype with one rule: **the app calculates, the model explains, a
person decides.**

1. **Overview** — electricity, production, energy intensity and potential additional cost for
   the period, plus a ranked investigation queue for the strongest candidates.
2. **Investigate** — one click asks the backend to compute the day's metrics and run a
   structured Gemini investigation.
3. **Evidence** — actual vs baseline intensity, the comparison window, deviation, threshold,
   operating hours, weather context, tariff and source are stored and shown as E1–E13.
4. **AI output** — summary, observations citing evidence IDs, possible contributing factors
   with the evidence still missing, recommended human checks, and limitations.
5. **Act** — the operator records an action, marks it in progress/completed with a note.
6. **Verify** — a before/after comparison over explicit date windows reports the observed
   change and states that other factors are not controlled.

Demo dataset: 1–30 September 2026, generated by formula (`synthetic-seed-v1`), labelled
`SIMULATED DATA` everywhere. The primary candidate is 17 Sep (+36.0% vs baseline, severity
Medium); 24 Sep is a milder second candidate; five days are reported as insufficient rather
than estimated.

## How the Gen AI is implemented (40% criterion)

- **Model:** Gemini `gemini-3.8-flash` via `generateContent`, called server-side only with
  the key in the `x-goog-api-key` header (never in the browser or a URL).
- **Minimum context:** a context builder packages 13 evidence items, one weather reading,
  units, sources, method version and explicit limitations. The model has no SQL, shell or
  tool access.
- **Structured output:** `responseMimeType: application/json`, temperature 0.2, a strict Zod
  schema for summary, observations, hypotheses, checks and limitations.
- **Evidence allow-list:** every cited evidence ID is checked against the supplied set.
  Unknown citations are removed and counted; the UI shows the discarded references.
- **Failure is a first-class state:** timeout (`MODEL_TIMEOUT`), quota (`MODEL_QUOTA`), HTTP
  errors and schema mismatch (`MODEL_INVALID_OUTPUT`) are stored as `FAILED`. No substitute
  answer is invented, and a failed re-run clears the previous result.
- **Provenance:** model name, prompt version (`investigation-prompt-v1`), method version
  (`baseline-v1`) and timestamp are stored with every investigation.
- **Honest fallback:** with no key, a deterministic mock produces a valid answer that is
  labelled **Simulated model**; the same UI shows **Live model** only when Gemini answered.
- **Rate limits:** 20 investigations/minute and 3 demo resets/minute per instance, so a
  public demo cannot be used to burn quota or wipe data repeatedly.

## Trust-by-design guardrails

| Risk | Handling |
| --- | --- |
| Model invents a number | Numbers come from the analysis engine; the model only receives and cites them |
| Model cites evidence it never saw | Allow-list validation, discarded citations are counted and shown |
| Model asserts a cause | Hypotheses carry confidence and the evidence still missing; language avoids “caused” |
| Weather mistaken for causation | Weather is context, not proof; limitations state this explicitly |
| Failed call presented as success | `FAILED` status with an error code and no AI panels |
| Simulated data mistaken for real | Header badge, data table labels, notice on Overview and the AI panel |
| Automated action taken | Recommended checks are human inspections; no equipment control is suggested or executed |

## Impact (25%)

- **Time:** replaces manual period comparison and spreadsheet archaeology with one queue and
  a stored investigation that can be reopened.
- **Money:** shows a potential cost estimate (`max(0, actual − expected) kWh × tariff`) with
  assumptions and formula, so a manager can judge whether a check is worth the effort.
- **Learning:** actions and before/after comparisons create a record of what was tried, even
  when the result is inconclusive.
- **Auditability:** every claim traces to a record, a formula and a method version — useful
  for internal reporting and future energy programmes.

No saving is claimed. The prototype demonstrates the workflow and the estimate; verified
savings require controlled studies on real metered data.

## Innovation (25%)

- **Evidence-first UX, not chat-first.** The product asks “what is this based on?” at every
  step, and the AI panel is a set of structured sections rather than a conversation.
- **Missing evidence as a feature.** Each hypothesis must state what data would confirm it,
  turning the model into a research assistant instead of an oracle.
- **Causation guardrail.** Verification compares two windows and explicitly refuses to
  attribute the change to the action.
- **Transparent heuristics.** The 15% threshold and seven-day baseline are named, versioned
  and described as prototype heuristics — not industry standards.

## User experience (10%)

- Dense but calm operations UI: KPI cards with units, SVG trend charts with textual
  summaries, severity badges with labels, tabular numerals.
- Empty, insufficient-data and failed states are designed, not hidden.
- Date-range filter, reset-demo control, health endpoint, and correlation IDs on API errors.
- Desktop-first; layout collapses to one column on smaller screens.

## Honest limitations

- The demo runs on **simulated** data; no real plant data has been processed.
- The 15% threshold and seven-day baseline are prototype heuristics, not industry standards.
- No authentication or multi-tenancy; access control must be added before multi-user use.
- Weather comes from a deterministic mock provider; the interface is ready for a real API.
- CSV upload is not implemented; date filtering is.
- Cost is a potential estimate at a recorded tariff, not a bill and not a verified saving.
- Rate limits are per Cloud Run instance; a shared limit belongs at the gateway.
